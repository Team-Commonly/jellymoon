# TOOLDESC: the tool descriptions and the server agree

Three things the schema advertises were reported refused by the server. Checked against main at a0b1c57.

## Decisions

- `post` with a `kind` other than `fyi`: the contract says the field is real. `MessageKind` is `result | ask | progress | fyi | error`,
  and ADR 0003 says "`post` is the PostInput command (F11)", with an ask's `needs`, `options` and `context` owned by the core.
  The server already accepts and stores every kind through the shared rule (`podcore/src/post.ts`, `COPIED`), the same in both
  adapters. The refusal was stale: the pod core's `post` command (f9fdd0f and the commits before it) replaced the old
  `message_post` that only stored `fyi`. What was still wrong was a sentence in `docs/development/e2e-contract.md` ("Input
  validation") that listed these fields as refused. Fixed. No schema change.
- `post` with a `taskId`: same line, same shape. `PostInput.taskId` is in the contract (ADR 0003: "a receipt's `taskId` is the
  task that woke the run, never the post's own `taskId`", so the post's own is a separate stored field). It is stored as sent.
  No schema change.
- `task_update` with a `note`: ruled (c), drop it. The ruling was the product-owner-delegated lead's call. Reason: the contract had
  no place for a note (`Task` has none, `task.updated` carries a `Task`), and a progress update already has a path: a `post` with
  `kind` progress and the `taskId`. `note` is removed from `TaskUpdateInput` and from the op text, `make gen` regenerated, the
  adapters' `refuse` helper is gone, and a task_update carrying a note is `invalid_input` at the edge as an unknown field. Red first:
  with the schema unchanged the new tests failed; after gen they pass. `e2e/input_test.go` keeps its 400 expectation (comment
  updated); it was compiled only (`go vet ./e2e/...`, `go build ./...`), not run.

## Tests

- `server/test/tool-desc.test.ts` (HTTP and `jm_post` over MCP) and `worker/test/tool-desc.test.ts` (the Worker's pod route over
  the real core): every kind, an ask with its parts, a `taskId`. These were green from the start: no red phase for `post`, because
  the server was already right. The `note` tests (the tool description lacks it; a note is refused at the edge) were red before `make gen`, green after.
- Mutant: dropping `taskId` from the fields the core copies fails 3 of the 13 new tests (server HTTP-adjacent, server MCP, Worker).
  Reverted, `git diff --quiet`.
