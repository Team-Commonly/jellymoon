# F17: every PR deploys its own Workers preview and the contract suite runs against it

**Changed.** `e2e-preview` now deploys the run's code to `jellymoon-spike-pr-<n>` (or `jellymoon-spike-main`) with its own Durable
Object namespace and D1 database (`worker/preview.sh`), runs the suite over HTTPS and the pod WebSocket, and tears both down in a
step that runs even when the suite fails. A missing secret fails the job instead of skipping. The suite gained a remote mode
(`JM_E2E_URL`, `JM_E2E_TEST_BEARER`); the closing-line judge moved to `e2e/judge.sh` and also fails a run that ran nothing. The
`worker` job runs `make test-worker` (it never ran a test); the `install` job is gone until `install.sh` exists.

**Evidence.** One live `make preview`-style run as `pr-0`: `E2E_MS=78327 STEPS=10/10`, then the Worker and database were gone.

**Next.** The operator sets `JM_CF_PREVIEW_TOKEN` and `JM_CF_ACCOUNT_ID` and swaps the required checks. F14 joins the preview run
with `JM_E2E_RUN: TestF14` in the workflow; F17 passes when F14 passes against the preview.

**Surprising.** Only five of the suite's tests can run on a deployed Worker; the rest need the fake clock or a restart.
