# F14: the whole slice as one test

**Changed.** `e2e/f14_test.go` adds `TestF14`, one walk of a person's path on F09's world: sign in (the test session route, one
`TODO(F15)` at that line), create a pod, invite, join; start the daemon and add the fake agent; assign it a task; the daemon claims the
wake; `task.claimed`; the agent's ask with the pod's receipt; a member's ruling; the second wake (`decision_ruled`); the agent's result and
`task.updated` done. It joins `par` and `suiteWG`, prints the suite's step lines, and is in the harness's `suiteTests`, so
`TestF14Budget` waits for it. A last step fails the walk at 60 s.

**Helpers.** `newF08` is split into `newF08Bare` (server, daemon build, config dir) and `joinPod`, and `newF09` into `newF09On`, so F14
can sign in inside its own first step; the other tests call the same constructors as before. The fake agent's script now accepts the string
`{{taskId}}` as an argument, replaced by the first `tsk_` id in its brief, because a script is written before the task exists.

**Two things the walk found.**
- The `decision_ruled` wake names the decision and the ask but not the task: the second brief has no `tsk_` id and the woken run's receipt
  has no `taskId`. The test does not assert either, and writes the task id into the second script by hand. A woken agent can find the task
  with `jm_task_list`, so this is a gap in what the wake tells it, not a failure. Whether the wake should carry the task is a product call.
- `jm_task_update` refuses a `note` (`this server does not store note yet`), so the script sends status only.

**Receipt and tool calls.** The evidence route (`GET .../runs/:run/tool-calls`) answers 404 on the public host by design (TestF11 checks
that), so the receipt's `toolCalls` is compared with what the agent recorded: two answered MCP calls (`jm_task_list`, `jm_task_claim`)
before the ask.

**Not done.** `feature_list.json` F14 stays `"passes": false` until the test passes in CI on both adapters.
