# F12: a member rules on an ask once, the agent is woken

**Changed.** The core gains a `rule` command (`podcore/src/rule.ts`): it checks the decision exists and is open, records
the chosen option and who ruled, freezes it, emits `message.updated`, and writes the `decision_ruled` wake through the
writer `change` uses. An ask now records its decision when posted. Both adapters only turn the `decision.rule` frame into
the command. `TestF12` and `podcore/test/rule.test.ts` are new; ADR 0003 moves rulings out of "Not here yet"; the podcore
cap rose 2,500 to 3,000 (ADR 0001 note, total 17,960).

**Fix pass r1.** `TestF12` now calls `par(t)` and `track(t)` and is listed in `suiteTests`, so the budget test waits for
it. The two 200 ms sleeps that stood in for "no stray second `message.updated`" are gone: the test posts an ordering
message from the asking run, waits for it on every member socket (and on a replay), and only then counts
`message.updated`. The log is ordered, so a stray update would arrive first.

**Evidence.** Red first (`TestF12` 0 of 5 steps, the core file 16 failing), then green on the server and the Worker.
Mutants caught by `TestF12`: already-ruled check, freeze, wake write, option check, and (r1) a `message.updated` emitted
on a refused ruling and on an `already_ruled` one.

**Next.** F13, then F14.

**Surprising.** `option` is a plain string in the command, not `optionId`: a key ending in `Id` is treated as a record key
by the core, so `constructor` as an option would have been `not_found` instead of "not on this ask". The feed route reads
only `message.created`, so it still shows an ask open after a ruling; members learn of it from `message.updated`. The
total stated at the top of ADR 0001 on main (16,740) did not equal its table (17,460); it now reads the real sum.
