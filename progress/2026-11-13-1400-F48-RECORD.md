# F48: a run's record names its repo, the commit it started from and the commit it ended as

On branch `f48-record`, one commit on top of `140dc7c` (F44). Gated: it changes what a run writes. Design: ADR 0017,
"Found while building F44". How it is built: `docs/development/run.md` ("What is kept", "What a kill leaves in the
record") and `docs/development/show.md` ("What the record names, and how far it is trusted"). Tests:
`crates/jellymoon/tests/f48.rs` and `tests/f48/` (`shown.rs`, `cut.rs`), 14 tests; the record's two example files
round-trip in a unit test in `run/record.rs`.

## What was built

- `runs/<id>/run.json` gains three names, each left out when it is not known: `repo` (the git folder the repo's
  checkouts share, as the system resolves it), `start` (the commit the copy was made from) and `end` (the commit the
  copy ended as). `repo` and `start` are in the record's first writing, before the harness starts. `end` is written
  in the one writing of the run's end, with `outcome` and `why`, for a run that finished.
- `run show` checks what a record names before git is asked anything: all three or none, each id 40 or 64 hex
  digits, the path from a root. Then the repo is found as F44 finds it and the git folder git names is resolved and
  compared with the record's; the branch's commit, as git printed it, must be the record's `end`; that commit's one
  parent, as git printed it, must be the record's `start`. No word of the record is an argument to git, and nothing
  is looked up at the record's path.
- Two new refusals, in fixed words: `the repo found for run <run> is not the one its record names, so its work is
  not shown` and `the work of run <run> does not start where its record says the run started, so it is not shown as
  the run's`. A branch that names another commit than the record's end takes F44's line, `is not as the run left it`.
- A record from before F48 names none of the three and is shown as F44 built it.

## What each end of a run writes

| A run that | `repo`, `start` | `end` |
|---|---|---|
| was refused before its copy, or at the lock runs are counted behind | no record | |
| was never started | written, then the record goes with the copy | no |
| finished with work | yes | the one commit made of its work |
| finished and changed nothing | yes | `start` (its branch is still there, or the run failed: see "After the gate") |
| finished with its copy's folder already gone | yes | `start`, by the same check |
| would have finished, and its branch was not at `start` | yes | no: it failed, as its branch was moved |
| failed, was stopped, ran out of time, could not be committed | yes | no |
| was cut off | yes | no; a look that writes `failed` adds none |

A kill at each step: the table in `run.md`, "What a kill leaves in the record".

## How a path is compared

A run writes the git folder as `fs::canonicalize` gives it. A look canonicalizes the folder git names for the repo
it found and compares the two part by part. The record's path is never canonicalized: that would ask the system
about a place a file chose, which on Windows can be a share on another machine. So a record that spells the same
folder in another case, through a link or with `..` is refused (one that differs only by a separator at its end, a
`.` part or a doubled separator compares equal, since paths are compared part by part). On Windows both sides are
the system's final path for the folder (`\\?\C:\...`), so case, short names and separators are the system's to
settle, once on each side.

## Not measured

- Windows and Linux: nothing was run there. Only `cargo clippy --target x86_64-pc-windows-msvc` for core and the
  binary. Whether `fs::canonicalize` gives one path for a folder reached by two drive letters or a `subst` is not known.
- A kill between `commit-tree` and `update-ref`, and between `update-ref` and the copy's removal: reasoned from the
  code's order, not tested. The tests kill while the harness works, and after the copy is gone before the end is written.
- A power loss: the record's new file is synced before it is renamed into place, and the folder is not synced,
  so the rename itself can be lost and the record be the one of the step before: an `end` missing for a commit
  the branch has, which `run show` refuses. That was not tested.
- A repo of the SHA-256 format: an id of 64 hex digits passes the check, and no such repo was made.

## After the gate: one more commit on the branch

The gate found that a finished run's `end` was whatever its branch named at the end, which need not be the run's
own commit. What changed:

- **At a run's end its branch must still be at `start`.** The branch is read by its whole name before anything is
  staged, and what git prints is compared with the commit the copy was made from. Otherwise the run has failed:
  `run <id> did not finish (its branch was moved while it worked): its copy is kept and no star was added`.
  Nothing is staged or committed, the branch stays where it was put, the copy is kept as a failed copy, the
  record says `failed` with `repo` and `start` and no `end`, and the wish is `needs_you`. `jellymoon copy clean`
  gives no start and takes the branch as it is, as before.
- **A finished run whose copy's folder was gone names `end` too**, which is `start`, by the same check. This was
  not in the ruling: without it core would write a record with two of the three names, which `run show` now
  refuses in every state.
- `run show` checks what a record names before it returns anything, so a run that changed nothing, and work that
  was kept or tossed, is refused on a record that names one or two of the three.
- A linked worktree is tested: the record names the git folder the checkouts share, and a look from either
  checkout shows the work.
- `JELLYMOON_TEST_RECORD_WAIT_MS` holds every writing of a run's record in a build with debug assertions.

Tests: 24 in F48 now (`tests/f48/moved.rs` 4, `linked.rs` 2, three more in `cut.rs`, one more in `shown.rs`).
Red first: the four in `moved.rs` and `shown::what_a_record_names_is_checked_whatever_the_state_of_the_work_before_anything_is_printed`.
Not red first, pins: the two in `linked.rs`, the three in `cut.rs`, each partial record and the forty `g`s in
`shown.rs`, and the `start` in F41's tidy test.

Mutations after the gate: 24, one at a time, against F48, F44, core's unit tests and F41, F39, F40. 23 killed.
The one that lives: a git that does not answer when the branch is read at a run's end is told as a branch that
was moved, not as work that could not be committed. No test has a git that fails at that one step. The review's
M14 (the wish names the run before the record is written) lived against F39 to F41, F44 and F48 and is pinned by
`cut::a_runs_record_is_written_before_its_wish_names_the_run`; M17 (a second end overwrites the first) was
already killed by F40.

Still open after this commit:

- Between the read of the branch and the record's writing, a branch that is moved under a copy that changed
  nothing is not seen: the run says it finished and names `start` as its end. A copy that changed is covered by
  git's own check of the old value when the branch takes the commit, and fails as `could not be committed`.
- A moved branch with the copy's folder gone fails in the same words, which say the copy is kept; nothing is.
- The three Windows faults in the tests were fixed by reading the code: nothing was run on Windows.

## Next

- F45 and F46 should refuse a record that names no commits. Whoever can write the home can take the three names
  out of a record and get F44's rule back; that is required of `run show` by F48's second step, and harms nothing
  while a look only shows.
- A run killed after its commit and before its end is written leaves a commit on its branch that no record names.
  `run show` refuses it. Nothing removes that branch.
- ADR 0017 says the three commands "take the work from the record, not from the branch's shape". As built the
  shape is still asked too, and a record from before is shown by shape alone.
