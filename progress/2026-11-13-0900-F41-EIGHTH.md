# PR 148's third gate: one rule for whether a left copy's branch goes

On branch `f41-fifth`, one commit on top of `0268252`. Gated: it changes which branch a look removes. Docs:
`docs/development/run.md` ("What is kept", "The one rule", "What the rule costs", "What is not closed") and
`copy.md`. Tests: `crates/jellymoon/tests/f41/held.rs` (new), `stood.rs` and `shapes.rs`.

## What changed, by the coordinator's ruling

1. **`base` is gone, whole.** The field of `Record`, where `copy::add` wrote it, the rule in `back::theirs`,
   its two tests, its lines in both docs and the lying-record entry in the not-closed list.
   - *A record that still has the field is read.* `Record` never refused an unknown field, so a `copy.json`
     written by a build of this branch reads as any record, whatever is at `base` (a number too, which made
     the record unreadable before). The word is not used, and is dropped when the record is next written.
2. **One rule.** `back::theirs` asks `rev-list --max-count=1 <branch> --not --exclude=<branch>
   --glob=refs/heads/* --glob=refs/tags/* --glob=refs/remotes/*`. A commit printed keeps the branch. No `HEAD`,
   no `refs/stash`, no `refs/bisect/*`, no other ref. `--exclude` holds for the one `--glob` after it, which
   is the branches'.
3. **The stood-on rules are unchanged and asked first**: `HEAD` naming the branch, the three files of a
   rebase or a bisect, a symbolic ref.
4. **What it costs** is in `run.md`: a copy made of a detached checkout, or of a commit amended away, leaves
   `jellymoon/run-<id>`. *No later look asks again*: the record goes at the look that kept the branch, so
   the name stays for good, also once a branch or a tag holds the commit. Only a branch or a tag there
   before the look lets it go. `git branch -D` removes it by hand.
5. Another left copy's branch counts as another branch: of two copies of one detached commit the first asked
   goes and the last stays (`held::of_two_copies…`).

## Not closed

- The name the rule leaves over is never removed by Jellymoon.
- A tag or a remote-tracking branch that held the commit at the look can be removed later (`git tag -d`,
  `git fetch --prune`); the commit then has no ref.
- A rebase or a bisect that starts between the look's question and its `update-ref -d` is not seen. Reasoned.
- `back::state` asks `symlink_metadata` and then opens: a FIFO put there between the two would hold the look.
- As before: another folder at the repo's path; `git worktree prune` between looks; a command killed inside
  git between the branch and the git folder; an orphan git child; an unreadable record never removed;
  `copies` removed or a link kept thirty days; Windows drives `canonicalize` cannot resolve; the thirty days
  tested by editing the record; the cut-off test uses a stalled git; the give-up line not said by the app or
  `jellymoon run`; a locked copy; a link left in `copies` at the give-up; a hand-made second repo that lists
  the copy; a commit reset away in the copy; something other than a plain file where git keeps a rebase's
  branch puts the take-back off thirty days.
- Windows is linted (`cargo clippy --target x86_64-pc-windows-msvc`) and not run here. Nothing new is
  Windows-shaped in core: the three `--glob` arguments are plain text handed to git.
