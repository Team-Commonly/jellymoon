# F43's reader, after the gate on PR 149: the test no longer races, and three corrections

Branch `f43-reader`, new commits on `fe2f52c`, with `main` merged in. Gated: it changes the reader.

- **Corrections to `2026-11-13-0200-F43-READER.md`.** Three statements there were wrong.
  - "The 20 seconds `support::jellymoon` gives any command": its limit is 90 seconds (`LIMIT`). The 20 seconds
    were the made-up session reaching its 200 MB cap at 10 MB a second; its 60 second cap could never be reached.
  - "With the bound in place the test cannot fail on timing": it failed twice at the gate with the bound in
    place, once reading `done` between its creation and its content, once with `capped` on a loaded machine.
  - "About 5 MB a second" for the debug reader: the gate measured 1.3 to 4.5.
- **The test does not race any more** (`crates/jellymoon/tests/growing_log.rs`). In a test's build the reader
  is held right after it has asked a log's length (`busy::pause("JELLYMOON_TEST_OPEN_WAIT_MS")` in
  `session::turns`, the pattern of `run.rs` and `run/cap.rs`). The test writes a log, starts `jellymoon day`,
  waits for the file the held command leaves, adds lines, and lets it go. The day holds what was there at the
  open: five lines when the last has no line break yet; five when a sixth was half written at the open and
  finished after, with more lines and another half line after it; none for a log that was empty at the open.
  With the bound dropped that is red at any speed, and so is a hold placed before the length is asked.
- **Every build, no seam.** The bounded reading is `session::read`, a function of a reader and a length. Core's
  test gives it a log that never ends and asks that it returns with the lines of its length and having taken
  exactly that many bytes (three lines, a line cut at the length, nothing, and more than the buffer holds).
- **A log at rest** has its own test on a small fixed log whose last line has no line break. No session.
- **The length, when the system will not say it** (finding 6): sought, to the log's end and back to its start.
  Only a log that can be neither asked nor sought is read whole. `length` takes what the system said and
  something to seek, and is unit-tested with a cursor and with a thing that cannot be sought.
- **The mark** (finding 4): a marked line after a blank first line is not kept, and a log that starts with two
  marks loses its first line.
- **Signal files.** The one file the test leaves is written as `go.tmp` and renamed. The file the held command
  leaves (`go.at`, written by `busy::pause`) is only ever asked whether it is there, never read here.
- **Deleted.** `crates/jellymoon/tests/support/fake_writer.rs` and its entry in `Cargo.toml`: nothing writes
  megabytes now. The old test `a_day_comes_back_while_a_session_goes_on_typing…`. The reader's unit tests moved
  out of `session.rs`, which was at 405 lines with them, into `session/tests.rs`.
- **Mutations**, one at a time, all killed: T1 (bound dropped: the test at the binary and core's), T2, T3, T4,
  B1, B2, M2, M3, M4, and five of this round: the length never sought, the log left at its end after seeking,
  sought though the system answered, held before the length is asked, never held.
- **Not closed.**
  - A release build has no hold, so the test at the binary cannot run against a release reader; there the bound
    is held by core's test alone.
  - A real file whose length the system will not say was not found; the seeking is tested on made-up things.
  - If seeking finds the end and the way back fails, the log is read from where it stands, which is its end.
  - M1 of the gate (`take(len + 1)`), alive then, is killed by core's test's exact count; no test at the binary
    kills it.
  - Not run on Windows or Linux here.
