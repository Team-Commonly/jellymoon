# First run: a new project named in the entry, and a folder dropped or chosen (F64, F66)

On branch `first-run-f64-f66`, one commit on `3f3bd31` (main moved on while it was built; the coordinator joins
it). The branch `first-run` was already taken by older work, so this one has its own name.

## What was built

A person who opens the window with no project on offer now finds the way in where the entry stands:

1. **F66, Start something new.** With no project on offer, page or none, the entry's place holds one chip,
   "Start something new", and a field whose hint is "Name a new project, or drop a folder here". Enter carries
   the name to core's `new_project` off the window's thread. Core's answer is one note: "Your new project is
   ready." with "“<name>” is ready: type what you want done.", or "No project was made." with core's
   refusal. The entry then is the wish's, with the new project's chip.
2. **F64, a folder dropped.** A folder dropped anywhere on the page's window goes to core's `add_project` off the
   window's thread, with or without projects on offer. "A project was added." or "That folder was not added.",
   one note; the path is never drawn. The project's chip is there at once, chosen, and the entry has the keys.
3. **Choose a folder.** Every entry of a day has "Choose a folder" after its chips: the system's folder picker,
   one folder, handed to what a drop does. Cancelled, nothing changes.
4. **The hint.** "What do you want done? Enter starts it."; with more than one chip "What to do? Tab: project.
   Enter: start.".
5. **The empty page says what to do here.** "Nothing wished for yet today." now says "Start in the field at the
   top: type what you want done, or name a new project."; a day with no session logs says "You can start here:
   name a new project in the field, or drop a folder on this window." in place of "Use Claude Code once and open
   Jellymoon again."
6. **Nothing typed is lost**: the kit keeps the words when the entry changes; a refused name stays.
7. **While the day is read.** A drop, a folder chosen or a name entered while "Reading your day…" is on show goes
   to core at once and its note is shown when core answers. When no entry offers the project yet, the window
   keeps its name and chooses its chip, with the keys, as soon as an entry offers it: the entry asked again at
   once, or the one a step of the reading gives.

The kit gained what the app could not do alone: an entry's `action` (a piece `action`, a tap `Tap::Action`),
`Page::on_paths` for a drop, and `Page::choose_option`. Core is unchanged.

## What was red first

One hold, against the code of `3f3bd31` (the new code taken out by a reverse patch, the new files moved aside).
`tests/f34.rs` was red on the old words of the empty page ("Ask one of your agents for something…"). Cargo
stopped after that binary (no `--no-fail-fast`), so the changed `tests/f42.rs` and `tests/f63.rs` (the hint's old
words, no entry on a day with no project) were not seen red. `tests/f64.rs` and `tests/f66.rs` name `starting.rs`,
which did not exist: they could not compile against the old code, and were not run there.

The first green round failed to compile `tests/f64.rs` (a closure's lifetimes); the second was green but for two
tests of `tests/f42/notes.rs` that held "no entry" where F66 now gives the new one (changed), and the window
test of a folder dropped after typing. The round after was green but for that same test: the drop never reached
the app.

The cause: GPUI's own drop (`on_drop`) runs only when the page's hitbox is hovered, and a hitbox is never hovered
while the last input was a key; a file drag is played as a mouse move, but the input kind is taken from the drop
event, so it stays "keyboard". A drag from the Finder moves no mouse over the window either: a person who typed
and then dropped a folder lost it. The kit now keeps the dragged paths on each drag move and gives them to
`on_paths` on any mouse-up while something is dragged. The other window test passed because a click came last.

The last hold: fmt check, `cargo xtask check`, clippy on the app and the kit, the app's `f64`, `f66`, `f42`,
`f63`, `f34`, `f43` and the kit's `entry`, `entry_band`, `entry_draw`, `entry_layout`, `field_draw`, all green,
then M5 alone against `f64`.

## What is open

- The row's "one choice, in core's words": core has no words for it; the app keeps ADR 0020's.
- A name core takes is not entered in the window on GPUI's test platform (core would start git with the test's
  own variables); it is proved through the made-up window, in a process of its own.
- A drop of several folders gives the first only.
- A day whose logs are there and are still being read: a project listed then has its note at once, and its chip
  when the reading gives the page; an entry that held no words is not shown until then, as before. That path
  (`window::reads` choosing the waiting chip) is not played in a test: the test platform runs no reading.
- A name entered while the day is read is not played in the window on the test platform (core's git, as above).
- Core's refusals of `project add` and `project new` are long and say `--repo` and `project new`; the app says
  them of "that folder" and "a new project" and keeps the rest.
- Windows and Linux were not run. A person's walk at a real window, a drop from the Finder and the real picker
  are owed.
