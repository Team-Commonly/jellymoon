# RUNEV: members hear when a run starts and when it ends

**Changed.**
- `schema/events.json`: two s2c events, `run.started {runId, agent}` and `run.ended {runId, agent, outcome}`, with `RunEndOutcome` (completed, cancelled, failed, expired) and three rules. `make gen` regenerated TS, Go and `docs/protocol.md`. Envelope fixtures for both, and an invalid outcome.
- `podcore/src/wakes.ts`: `run_claim` emits `run.started`. `podcore/src/claims.ts`: `endRun`, the one place a run ends, emits `run.ended` after the run's claims are released. The run cap now ends a run as `expired` for members; the stored outcome stays `failed`, because the operations' `RunOutcome` has no `expired`.
- Both events are seq'd (`emit`), like `claim.released`: stored and replayed on subscribe, so a client that reconnects learns a run ended while it was away. Presence stays live and unchanged.
- Members only: both adapters send seq'd events to subscribed sockets, and only a member can open a pod's socket.

**Evidence.** `podcore/test/runev.test.ts` covers the start, each ending path (the daemon's completed, failed and cancelled, run_stop, the 2 h cap), a lease expiry ending no run, once only, and refused stops and ends emitting nothing: 8 of 11 red before the change, 11 green after. `e2e/runev_test.go` (TestRUNEV) was STEPS=1/5 on both adapters before the change and 5/5 after; the full set is green on e2e-c and e2e-a. Two existing podcore tests that counted a run's events now count `run.started` and `run.ended` too.
