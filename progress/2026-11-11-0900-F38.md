# F38: a run gets its own copy of the repo (`jellymoon copy make`, `copy clean`)

- **Done.** Core's `make_copy` and `clean_copy` (`copy.rs`, `copy/git.rs`), the two commands, ten tests at the binary
  (`tests/f38.rs`, `tests/f38/hostile.rs`), the smoke step `copy`, and `docs/development/copy.md`. F38 passes.
- **Decided.** Cleanup reads nothing from the copy: git is always told `--git-dir` and `--work-tree`, started in an
  empty folder with a short list of variables. The commit is made with plumbing. Exclusivity is create-new on
  `runs/<id>`; `tap.rs` is not touched. A run id is core's own shape, `r` and sixteen hex.
- **Surprises.** `git add` starts a second git inside a folder at a submodule path, under that inner repo's own config:
  a filter an agent wrote there ran. Those paths are left out of the add, so a submodule change is not committed. And
  a test's plain folder inside this checkout made git find this repo itself and add a worktree and a branch to it;
  both were removed, and `GIT_CEILING_DIRECTORIES` (core, tests, smoke) with a test now holds it.
- **After review.** Each git child has five minutes and is then killed; a `make` stopped so takes its half-made copy
  back. One clean works at a time, under the system's lock on `runs/clean.lock`. A run id whose branch is still
  there is refused, so taking a copy back can never delete an earlier run's work.
- **Next.** F39 calls the two functions and must end the run before `clean_copy`. Open: run branches are never
  removed, a killed git can leave its own lock file, Windows and Linux are proved only by CI.
