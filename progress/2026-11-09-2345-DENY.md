# DENY: "This wasn't me" refuses a sign-in code the person did not start

**Changed.**
- `schema/pod-api.json`: `POST /v1/auth/device/deny` (auth user, `DeviceDenyRequest {userCode}`, `DeviceDenyResponse {}`) and its rule; `schema/common.json`: the error code `access_denied` (400, RFC 8628). `make gen` regenerated TS, Go and `docs/protocol.md`. ADR 0008 step 4 carries the route and its rules.
- Both adapters: approve and deny share one handler, so a refusal of deny is approve's answer for the same code, byte for byte (unknown `not_found`, expired `expired_token`, approved, refused or exchanged `gone`, whose message is now "This code was already used."). Deny marks a pending, unexpired code `denied` and is idempotent; approve skips a denied code; the token poll answers `access_denied` before `slow_down`. The server adds `device_codes.denied` in place; the Worker adds it in `schema.sql` and `worker/migrations/0002_device_deny.sql`.
- Approve has no rate limit, so deny has none either: "the same rate limit as approve" is none. The e2e step proves deny and approve still answer with the start limit spent.
- `jellymoon login` stops on `access_denied` with `jellymoon: the sign-in was refused in the browser`, exit 1, no retry.
- Web: `/device` shows "This wasn't me" beside Approve. Success shows "Code refused" with no Approve; deny's refusals show the unknown-code line. Approve's 410 line now reads "This code was already used."

**Evidence.** `e2e/deny_test.go` (TestDENY) was STEPS=1/8 on the server before the change, 7/8 with the routes but before the CLI change, and 8/8 after; on the Worker 1/8 with the deny route taken out and 8/8 with it. `server/test/device-deny.test.ts` 0 of 5 before, 5 of 5 after; `worker/test/device-deny.test.ts` 0 of 5 before, 5 of 5 after. The CLI test failed before and passes after. Web: 9 tests red before, all green after. The browser specs list 44 tests (22 x 2) and type-check; CI runs them.
