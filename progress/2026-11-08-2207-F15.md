# F15: jellymoon login through the server's own device flow

**Changed.** The server mints its own device code and a person approves it from a browser session that GitHub's OAuth web
flow signs in (ADR 0008). New routes in both adapters: `POST /v1/auth/device/approve`, `GET /v1/auth/github/start` and
`/callback`, `GET /v1/me`, and the contract's `POST /v1/auth/device` and `/token`. `jellymoon login` polls, writes
`user-token` at 0600 and prints only `Signed in as <login>`. F15's stale step was rewritten to the contract, per the owner's
ruling, and F15 passes.

**Evidence.** TestF15 was committed red (0/11 steps on the server) before the implementation, then 11/11 on the server
(twice) and on the Worker. Nine mutants, each caught: one-exchange, 0600 (unit and e2e), GitHub 401, state binding, one-use
state, next, approve CSRF, GitHub token logged, GitHub token stored.

**Next.** BSESS: the session cookie on the pod socket (with an Origin check) and the other user routes. User token expiry.
After #18 lands, add `jellymoon login` to the usage line in `cli.go` (left out to keep off #18's line). List ADR 0008 in
`docs/INDEX.md`.

**Surprising.** The token-not-stored check works black-box: the stored-token mutant shows up in PGlite's WAL file under the
data dir at once, so the suite can prove a secret was dropped.
