# PR 148's fourth gate: a take-back deletes the run's own name, never what a name points at

On branch `f41-fifth`, one commit on top of `219db49`. Gated. Docs: `docs/development/run.md` ("What is
kept", "The one rule", "What is not closed") and `copy.md`. Tests: `crates/jellymoon/tests/f41/pointed.rs`
(new) and `shapes.rs`.

## What changed

1. **The delete is `update-ref --no-deref -d <name> <commit>`** in `copy/back.rs`, with the commit `rev-parse`
   gave for the name before the question. A name that moved makes git refuse. For a look that is a failed git
   step: the record gets `put_off` and the next look asks again. For the command's own take-back it is the
   error any failed git step of it is.
   - In `copy.rs`, for a copy that could not be made, the commit is the one the copy was to be made at
     (`base`, which `add` has), so that place has an old value too.
2. **A run's name that is itself a symbolic ref is kept**, untouched, and the rest of the copy is taken back
   (`symbolic-ref --quiet <name>` in `back::theirs`, before the `rev-list`).
3. **Replace refs and grafts are off for the question.** `--no-replace-objects` on the `rev-list`. git has no
   option for grafts; it reads `GIT_GRAFT_FILE`, so that one call is given a name in the empty folder git is
   started in, and the repo's `info/grafts` is not read. Seen by the test, on git 2.50.1.
4. The made-up git (`tests/support/fake_git.rs`) runs the real git once with the lines of a file `first`
   just before the step it is to stall on: something that happens between two of a look's git calls, with
   no race.

## Tests, and whether each was red on `219db49`

- `pointed::a_run_s_name_made_a_symbolic_ref_is_kept_and_the_branch_it_points_at_is_not_deleted`: red (`main`
  was gone). Three targets: `main` checked out, a branch with its only commit, a branch in another worktree.
- `pointed::a_commit_that_lands_between_the_question_and_the_delete_keeps_the_branch`: red.
- `pointed::a_replace_ref_or_a_graft_does_not_stand_for_a_commit`: red.
- `pointed::the_command_s_own_take_back_deletes_its_name_and_not_the_branch_the_name_was_made_to_point_at`:
  written after the fix; fails with `--no-deref` dropped, which is what `219db49` ran.
- Never red, each holds a line the gate's mutation survived: `pointed::a_question_git_cannot_answer…` (A2),
  `shapes::a_branch_another_ref_is_a_name_for_is_kept` with a symbolic ref under `refs/remotes` (A12),
  `pointed::a_worktrees_folder_that_cannot_be_listed…` (A15; Unix only, and skipped for an account a mode
  does not keep out. The folder is mode 300: at 000 the copy's git folder cannot be reached and the look
  stops earlier, at `record::asked`).

The two survivors are the take-back of a copy that could not be made. A test needs a branch or a symbolic
ref of the run's name to appear between `add`'s check and git's `worktree add`, and the run's id is not
known to a test before the command prints it. Reasoned: the name was checked absent a moment before, and
git made it at `base` or not at all.

## Not closed, new

- The two survivors above.
- A never-started run's own take-back removes its branch without asking; if that branch was what let a left
  copy's branch go a moment before, a commit made on a detached `HEAD` loses both names. In `run.md`.
- `GIT_GRAFT_FILE` is read from the folder git is started in. That folder is checked empty when git is found,
  not at each call.
