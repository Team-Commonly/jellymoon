# F19H: connector hardening, the open follow-ups of F19

**Changed.** Four items from ADR 0009's "Still open" are closed, and the ADR describes each.
- *The crash window.* A released write with no upstream answer, older than a 60 s answer budget, settles as the new outcome
  `unknown` with the reason "sent at most once, outcome not recorded". It settles on start (`Hub.restore`) and before each
  receipts read, and it is never sent again. A late answer still replaces it.
- *A receipt for every read.* A read catches the egress check, the vault and the adapter. Each failure becomes a `failed`
  receipt with a fixed reason, and the agent gets `upstream_failed`. Receipts gained an optional `reason`. Before this, a
  vault failure answered 500 and wrote no receipt, and a thrown value reached the server log through `app.onError`.
- *The approver set.* `POST /v1/pods/:pod/approvers {connectionId, userIds}` is owner only and takes members only, each once.
  An empty list clears the set. A pod owner or a listed member rules on that connection's writes, and anyone else, a removed
  approver included, gets `forbidden`.
- *A slow upstream.* A released write's call now runs outside the pod's command queue and the socket's frame chain, and its
  answer comes back through `PodRuntime.serial`. Members hear of the ruling at once, so the receipt reads `released` with no
  status until the answer lands.

Egress also refuses 2001:db8::/32, and the ADR says a timed-out lookup is abandoned, not cancelled.

**Evidence.** The red commit failed 8 unit tests, the classifier among them, and TestF19 went `STEPS=6/7` (the approver route
answered 404). The tree is now green: 250 server and podcore tests, and TestF19 `STEPS=7/7` with the e2e-c settings. Each
mutant was applied, run and reverted with a clean tree:
- the settle never runs: caught by the two crash-window unit tests;
- a throwing read skips its receipt: caught by the four throwing-read unit tests;
- the approver check passes any member: caught by TestF19 steps 5, 6 and 7;
- the release awaited inside the pod's chain again: caught by the slow-upstream unit test.

**Deviations.** The red commit carries the test seam its unit tests inject an adapter through (`AppOpts.adapter`, `Kit.adapter`),
so that its failures are the behaviour and not the setup. It also carries a cap raise, because the pre-commit entropy gate reads
the working tree. The approver step is TestF19's fifth step, not its last: after step 5 expires a write, the first run's token
is dead, and a second run wakes nothing. Steps 5 and 6 now count writes from where the approver step left them, and they wait
for a released write's answer instead of assuming it lands before the ruling is announced. The 0001 note on the red commit
gave the total as 26,940; it was 26,980, and the next note corrects it.

**Lines.** Measured against main (bc999d0) at the implementation commit, server and e2e together: +404 / −69. Removed: the
claim that members hear of a ruling only after its call, and three "Still open" entries. Caps: server 3,710 and e2e 7,530.

**Open.** Nothing reconciles an `unknown` write against the upstream, so a person checks it. Names that resolve publicly but
route internally, and the one check per call, stay open as before.
