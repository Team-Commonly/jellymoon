# F18 PR 4: the /device screen, device.spec and invite.spec

**Changed.** `web/src/DeviceScreen.tsx` is `/device` inside the same Shell. It reads `?code=` and shows it. Signed out, it links to
`/v1/auth/github/start?next=<encoded /device?code=...>`, so GitHub brings the person back with the code kept. Signed in, the code sits
in an editable box and Approve sends `POST /v1/auth/device/approve` once (a ref guards the double click); loading the page approves
nothing. 404, 410, 400 (expired), 401, other and network failures each say what failed and leave Approve available. `http.ts` gained
`me()` (GET /v1/me, 401 is null), `approveDevice()` and `signInHref()`. `main.tsx` now asks `me()` before the first render, so
`signedIn` is the cookie's truth instead of a hard-coded `false`. `InviteScreen` uses `signInHref` too (see Surprising).
`web-e2e/device.spec.ts` and `invite.spec.ts` run at 390 and 1440; `fixtures.ts` gets `signIn(page, person)`, which sets the session
cookie GitHub's callback would set. The cap note `docs/entropy/caps/2026-11-09-web-1580-to-1750.md` raises web; browser-specs.md lists the two specs.

**Evidence.** vitest web 90 passed (12 new for /device; the invite test's link expectation changed). `bun run check:types` clean,
including tsc over web-e2e. `playwright test -c web-e2e --list` enumerates 10 tests (5 per project). `make entropy` and `make private`
green, `make check-gen` green. No server file changed, so no server tests. A scratch script against a real local server confirmed the
contract the specs lean on: `/v1/me` by cookie is 200 and 401 without, approve by cookie with the server's Origin is 200, an unknown
code is 404, and the token poll then returns a `jmu_` token. The specs themselves have not run: browsers are installed in CI only,
so the first run is the PR's `browser` job.

**Not here.** layout.spec (PR 5b); `feature_list.json` F18 stays false. The Shell header still prints "Not signed in" and a dead
Sign in button whatever the session is. The specs for the pod use the socket bridge still; invite.spec is the first to open the pod
over the cookie socket directly.

**Surprising.** `InviteScreen` linked to `/sign-in?return=...`, a path no server route answers (the server's own route is
`/v1/auth/github/start?next=`); on a built client it landed on "Nothing here." Both screens now share `signInHref`. And the client had
no way to learn it was signed in: `signedIn={false}` was hard-coded in `main.tsx`, so the browser sign-in worked on the server and was
invisible to the page until `me()`.

**Review fix.** The one review found `acceptInvite` sent a cookie write with no JSON body or Content-Type, which the server refuses (403), so Join failed in a real browser and invite.spec would have timed out. It now sends `content-type: application/json` and `{}`. `web/src/http.test.ts` pins the request shape (method, content-type, body, credentials) of every client call; it was red on accept before the fix. Also: 403 on Approve no longer says "Try again", 401 offers a sign-in link back to the code, two stale comments about where an invite code appears are corrected. Web vitest is now 95 passed; web cap 1,810 (new cap note).
