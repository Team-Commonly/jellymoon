# F53: a follow-up

On branch `f53-follow`, built on main after F52 (#173) and replayed on main after F62 (#176). The account is
`docs/development/wish.md` ("A follow-up"), `run.md` ("A follow-up's run"), `keep.md` ("A follow-up's work"),
`toss.md` ("Work a follow-up stands on"), `show.md` and ADR 0018, "Found while building F53".

The replay joined two changes to a run's start (`run.rs`): the folder is found as F62 finds it, on the day's
logs or on the list, and a copy that is refused is said in F62's words; the copy is then made at the followed
work. A follow-up whose project is found on the list alone is played since the gate (`tests/f53/gate.rs`).

## What changed

- **`jellymoon wish --after <id>`** makes a made wish that names the wish it follows (`after`, last in the kept
  wish) and takes its project. It is refused, in one fixed sentence each, unless that wish's run finished with
  work that waits or was kept (`run/follow.rs`, `followed`).
- **`jellymoon run` of a follow-up** takes the keeps' lock, reads the followed record, makes its copy at the
  followed work's commit while that waits and at the checkout's once it was kept (`copy.rs`, `Base`), and
  starts the harness with `--resume <followed session> --fork-session --session-id <new>`. A harness that
  keeps that session no more is started once more with a new session; the record's `follows` and `forked` say
  which (`follow.rs`, `Go::started`).
- **The order.** `run keep` of a follow-up is refused while the followed work waits; `run toss` of work is
  refused while a follow-up's run stands on it (`follow.rs`, `keep_first`, `toss_first`).
- **A keep after a joined keep.** `copy::Keep` gains `held`, the commit the followed work was kept as, and git
  is given the run's start as the merge's base (`copy/keep/made.rs`).
- **Moved, not changed:** a run's fixed lines are in `run/words.rs`, and a keep's `done` in `run/keep/done.rs`,
  to keep `run.rs` and `run/keep.rs` under the file limit.
- **The smoke chain** has a `follow` step (`crates/xtask/src/smoke/follow.rs`).
- **Three items of F52's gate:** wish.md's "Not closed" sentence on a key over more than eight lines, "only
  marks" naming any other sign, and two more cases in `still.rs` (a two-line key id with a word at both ends,
  and an id in ten lines between spaces), each failing with its reading taken out.

## What its gate found

The gate failed on three blockers and gave four notes. Each has its case in `tests/f53/gate.rs`, seen failing
before its fix.

- **A keep after a joined keep, on git 2.38 or 2.39,** brought back followed work the person had taken out
  since: with `n.txt` removed again and `b.txt` restored by a commit of theirs, `run show` listed one file,
  `keep --ask` said `fits: true`, and the keep landed `D b.txt`, `A n.txt` beside the follow-up's file. Such a
  git cannot be told the merge's base. That keep is now refused there in one sentence, `--ask` says `fits:
  false` with it, and nothing is changed (`copy/keep/made.rs`, `Unkept::NoBase`). On the real git, 2.40 or
  later, the same case lands the follow-up's change alone.
- **A moved branch, or another repo, with a folder that was typed in or listed** was said as a folder a run
  cannot copy, which was false. `Base::commit`'s refusals are a run's now, said alone, and the sentence for
  another repo names no `--repo` (`copy.rs`). Both are played with the folder named, typed in and listed.
- **A follow-up of waiting work that changed nothing** said its branch `is where the checkout was`. It says
  `is where the work it follows ended` when its `start` is the followed run's `end` (`run/follow.rs`,
  `ended_as`), and a look believes that line too (`end::recorded`).
- **A fork that worked before it said its session is lost** was started again in the changed copy: one commit
  held both starts' changes under `forked: false`. It is started again only in a copy that is as it was made
  (`copy::as_made`); else the run has failed, in an eighth kind of a failed end (`asks::WORKED`).
- **A follow-up of kept work, in a checkout without that work,** started at the old commit under a fork. The
  run is refused unless the checkout's history holds the commit the followed record names as `kept`.
- **`keep_first`'s `was.end == record.start`** had no test: a follow-up made after a joined keep, with the
  branch put back to the kept commit, is now refused by history, and is kept with the condition taken out.
- **The busy lock** said `another keep or toss`, also when a follow-up's start held it. It names all three.

## What the next session should know: open rows

1. The fork was not run on a real harness with core's command line.
2. A follow-up made and not run, whose followed work is then tossed, is refused on every run. The reviewer
   saw: `run toss` says it has had no run, `run stop` says no run is going, the page keeps it `working`, and
   it holds one of the day's eight. Nothing lets a wish with no run go.
3. The order of a toss is read from the day's made wishes. The reviewer took `after` out of the kept wish by
   hand: the followed work was tossed while the follow-up's work waited. The follow-up's keep was then refused
   by history, so nothing landed wrongly.
4. A fork that committed in its copy, or left only an ignored file, before it said its session is lost is not
   started again by `copy::as_made`, and no test plays either: the made-up agent starts no git.
5. A follow-up of work kept by moving the branch forward, run before the person commits again, starts at the
   commit that work ended as, and one that changed nothing then says `where the work it follows ended`: true,
   and not the words of a run made where the checkout stood, which would be true too.
6. Decision 9 says a toss is refused for a waiting follow-up; the build also refuses while the follow-up's run
   goes or asks. ADR 0018 says so under "Found while building F53"; the decision's own sentence is as it was.
7. The rows of `2026-11-15-0215-F52-SECOND-GATE-FIX.md`, still open.
