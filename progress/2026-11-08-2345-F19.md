# F19: an agent reads Linear through a pod grant without ever holding the Linear token

**Changed.** The connector layer lives in the pod-state server (ADR 0009). A pod owner connects a vendor and grants an agent
`read` or `write-with-confirm`; the credential is stored only as an AES-256-GCM envelope under `JM_VAULT_KEY` (a key ring, one
key id per row). A connect compares the upstream's operations with the repo's pin (`server/connectors/linear.json`) and refuses
drift with `connector_drift`. `connector_call` reads at once; a write parks as the agent's own ask with its exact arguments, the
ruling's transaction claims the parked row once, and approve releases exactly one upstream call before members hear of the
ruling. Reject and expiry (24 h, a new pod core deadline: `expiresAt` on an ask, a late ruling gets `gone`) release nothing.
Every call leaves a server-stamped receipt (`connector_receipts`). Only `server/src/upstream-mcp.ts` knows MCP. The Worker is not
built for it: `TestF19` is on `E2E_A_SKIP`, documented in `docs/development/e2e-contract.md`.

**Evidence.** `TestF19` was committed red (`E2E_MS=5533 STEPS=0/6`) and is green with the e2e-c settings (`STEPS=6/6`). Five
mutants, each applied, run, reverted with a clean tree after: the release not consuming the parked call (step 6, and the
unit test of the once-only claim), the token in an error (step 3), the read skipping the grant check (step 1), the drift check
skipped (step 1), a reject releasing (step 5).

**Deviations.** The pinned operation's name def is `ConnectorOperationName` (the first name clashed with a generated type); the
rename rode in the implementation commit because the pre-commit entropy gate reads the working tree. The ADR is 0009 (0008 is
held by an open change). The harness gained a per-server environment (`startServer(t, env...)`) to carry the vault key.

**Review follow-ups.** Only a pod owner rules on a connector write (a plain member's ruling is refused forbidden, step 5);
the scrub also drops the credential \u-escaped, URL-encoded and base64-encoded (step 3 probes each); an upstream answer over
1 MiB is refused with `upstream_too_large`. New checks catch the four mutants the review found surviving: a write class
read from the call's input (step 4), a connection lookup ignoring the pod and a grant lookup ignoring the connection (unit,
`server/test/connector-keys.test.ts`), and a fixed IV (unit). The server cap is 2,800.

**Egress (CodeRabbit, upstream.ts:33).** The literal url check let `localhost.` and any name resolving inside through. Now
`server/src/egress.ts` normalises the host, classifies addresses by parsing them, resolves the name before every upstream
request (connect, each read, each release) and pins the request to the checked address with the name kept for Host and TLS.
The server cap is 3,200.

**Open.** Any member can approve a write; DNS names that resolve to private addresses are not caught; a crash between the claim
and the call leaves a released row with no upstream status (at most once). See ADR 0009, "Still open".
