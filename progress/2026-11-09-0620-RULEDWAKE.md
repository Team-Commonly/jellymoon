# RULEDWAKE: a ruling tells the agent what won, and the task it was about

**Found on main before the change.**
- Wake refs carried only `decisionId` and `messageId` (`podcore/src/rule.ts`, the `writeWake` call; schema `WakeRefs` had no option or
  task field), so a woken agent could not tell which option won, nor which task the ask belonged to.
- The feed of both adapters (`server/src/routes-ops.ts` feed, `worker/src/pod-routes.ts` feed) built messages from `message.created`
  only, so after a ruling an ask still read `decision.state: open`; only the socket's `message.updated` showed the ruling.
- `jm_task_update` refuses a `note` on purpose: `TaskUpdateInput` is `{taskId, status}`, ADR 0003's 2026-11-08 line rules it out, and
  `server/test/tool-desc.test.ts` plus `worker/test/tool-desc.test.ts` pin the refusal. Left as it is.

**Changed (one shared path, `podcore`).**
- `schema/events.json`: `WakeRefs` gains `optionId` (an `OptionId`), regenerated into `gen/`, `daemon/internal/protocol/gen.go` and
  `docs/protocol.md`. `jm_read`'s description now says an ask carries its decision as it stands.
- `podcore/src/rule.ts`: the `decision_ruled` wake carries `decisionId`, `messageId`, `optionId` and, when the ask was attached to a task,
  `taskId`. New `overlayDecisions(state, messages)`, used by both adapters' feed. `podcore/src/post.ts` keeps the ask's `taskId` on its
  decision record; `podcore/src/types.ts` and `podcore/src/wakes.ts` (`optionId` joins the ref kinds a pending wake merges).
- `server/src/routes-ops.ts`, `worker/src/pod-routes.ts`: the feed passes its messages through `overlayDecisions`.
- The run's brief already prints every ref, so the second run's brief now reads `taskId tsk_... , optionId a` with no change to the brief.
- `e2e/f14_test.go`: the hand-written task id is gone. The ask carries `{{taskId}}` and the finishing script borrows it from the brief; the
  walk asserts the second brief names the task and `optionId a`. `e2e/f12_test.go` asserts `optionId b` on the wake and that the woken run's
  feed shows the ask ruled with option b.
- `docs/adr/0003-pure-pod-core.md`: the refs sentence and a 2026-11-09 line. Cap note `docs/entropy/caps/2026-11-09-ruled-wake-names-task.md`.

**Evidence.** Tests first: the new server and Worker tests and the podcore refs test failed before the code (refs lacked `optionId` and
`taskId`; the feed showed `open`). After: `bun test podcore` 169, `bun test server` 101, `bun test worker` 46 pass; `check:types` clean;
`TestF12` and `TestF14` pass against the server (`make e2e-c` shape, PGlite) and against the Worker (`worker/dev.sh`).

**Open (a product call, not made here).** `jm_task_update` still takes no note. If agents need one, the contract needs a place to keep it
(a `note` on the task, or a progress `post` with the `taskId`, which exists today).

**Surprising.** A ruling that folds into a pending wake keeps that wake's earlier ref of a kind (ADR 0003), so a pending `task_assigned`
wake can carry its own `taskId` beside the ruled decision's ids. Both ids are real; the reader should not assume they match.
