# F77-CHILD: a harness started from inside a Claude Code session is not told it is that session's child

**What changed.** On branch `f77-child`, on main `4fac595`. Tests, two docs and three lines of core; no app, no kit.
- `crates/jellymoon/tests/f77.rs`: `jellymoon` is started with `CLAUDECODE`, five `CLAUDE_CODE_*` variables, two
  of them spelled again as Windows would still take them (`claudecode`, `Claude_Code_Entrypoint`), and every
  variable of both systems' lists. The made-up harness's recorded names are this system's list and no other, for
  six starts: the reading call, a run, an answer, a follow-up's fork, a follow-up started again under a new
  session, and a run started apart by `wish --run`.
- `call.rs`: the two lists are both built on every system (`UNIX`, `WINDOWS`; `ENVIRONMENT` picks one), so one
  test in core holds each to `page.md` and `run.md` wherever it runs. What a harness is started with is unchanged.
- `page.md` and `run.md` give the Windows list name by name, and say that no `CLAUDECODE` and no `CLAUDE_CODE_*`
  variable is passed.
- Nothing was added to the test support: `fake-claude` and `fake-agent` already record their variables.

**The evidence.** The code already cleared the environment and passed a fixed list, so the six tests of a start
were green as written: they are pins. Red first were the two tests of the docs, at the binary and in core: neither
doc listed the Windows variables. Nineteen one-rule mutations, each killed:

**Where core starts a program.** Four places. The harness, always through `call::harness_of` (`call.rs`): the
reading call, the check before a run, an answer (`run/answer.rs`) and the three starts of `run/follow.rs` (a first
run, a fork, a second start); no copy of the list. git (`copy/git.rs`): cleared, with a list of its own passed
through the same `call::passed_on`. `/bin/ps` (`run/dead.rs`): cleared, two fixed variables. `jellymoon run`
started apart (`run/apart.rs`): the one start that inherits everything, on purpose, since it is Jellymoon itself;
its harness is started through `harness_of` like any other, and a test holds that.

**Windows and the spelling of a name.** The code never asks for a `CLAUDE` name but `CLAUDE_CONFIG_DIR`: the
environment is cleared and each listed name is looked up, which Windows does without regard to case, and passed on
under the list's own spelling. So `claudecode` is not passed there or anywhere. The test sets both spellings on
every system, takes any recorded name that begins `CLAUDECODE` with its underscores and case put aside as a
fault, and on Windows compares the recorded names with the list in capitals.

**What's next.** Windows and Linux: nothing here was run there. The Windows half of the pin (what the made-up
harness sees there is the Windows list, all fourteen) is first run by CI. If a Windows child is given a variable
by the system that no parent set, that test fails there and names it.

**Surprising.**
- No variable is on the list that begins `CLAUDE_CODE`; nothing had to be ruled on. `CLAUDE_CONFIG_DIR` stays.
- A person who signs in to Claude Code only through a variable (`CLAUDE_CODE_USE_BEDROCK`, a token in
  `CLAUDE_CODE_OAUTH_TOKEN`, `ANTHROPIC_API_KEY`) has a harness that is not signed in when Jellymoon starts it.
  That was so before this row; `page.md` now says it. Whether that is wanted is the coordinator's to rule.
- `follow.rs` starts the harness with no fork when the followed run kept no session. It is the same line a first
  run takes (M14), so no test of its own was written for a follow-up of such a run.
- The binary's budget had room for the 220 lines of the new test; only core's was raised, by 20.

**Deleted.** The two `cfg` lines over the lists in `call.rs`, and the docs' "the system's equivalents ... and the
like" and "or the Windows list", each replaced by the list. Lines: 259 added, 8 removed, before this note.
