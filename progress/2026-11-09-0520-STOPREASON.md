# STOPREASON progress (2026-11-09-0520 UTC)

**Changed.** The daemon read the `stopReason` of an ACP `session/prompt` reply nowhere, so a run the agent ended with `refusal`, `max_tokens` or `max_turn_requests` was still reported to the pod as `completed`. `turn` in `daemon/internal/acp/acp.go` now passes the reply to `stopReasonErr`, which turns those three into an error; `claim` in `daemon/internal/daemon/run.go` already ends any error from `acp.Run` as `failed` (and the workspace is kept, as for any failed run). The error text names the stop reason and is logged, as every failure reason is; the end-run wire has no reason field, so none was added and the schema is unchanged. `end_turn` stays completed. `cancelled` is not judged there: a stop the client asked for already comes back as the stop's cause. A missing or unknown stopReason stays completed, a commented choice, so a harness that omits it or adds a value does not start failing every run.

**Evidence.** `TestStopReasonDecidesTheTurn` (table over seven stop reasons, through `Run` and a fake agent mode `stop:<reason>`) was red before the fix for the three failing reasons, `Run = <nil>`, and is green after. `go test ./daemon/... -count=1 -race` is green, `TestReplayClaude` and `TestReplayCodex` included. To make room under the 60-line function limit the fake agent's `ask-other` body moved into a helper, unchanged. The daemon LOC cap went 4,840 -> 4,910 (measured 4,907) with a note.

**Next.** If the pod ever wants to show why a run failed, the end-run call needs a reason field; that is a schema change and a decision for the protocol owners.

**Surprising.** Nothing needed the schema: the failure path already collapsed every error into one outcome, so the fix was one function and the rest was test.

**Known limits.** The reason reaches only the daemon log, not the pod. A stop reason added by a future ACP version is treated as completed until it is named here.
