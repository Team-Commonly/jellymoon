# BSESS: a browser signed in through F15 uses the pod by its session cookie

**Changed.** One authentication function per adapter (`authOf` in `server/src/kit.ts` and `worker/src/auth.ts`): a Bearer
first, else the `jm_session` cookie on any route a person may call, which must hold a `jmu_`. A cookie state change needs a
JSON content type and the server's own Origin (none is refused); the pod socket by cookie needs the same Origin. Run- and
computer-only routes and `POST /mcp` stay Bearer-only. New `POST /v1/auth/logout` revokes the presented token and clears
the cookie. ADR 0008 has the rules in its new "Browser session" section.

**Evidence.** TestBSESS was committed red (STEPS=2/8 on both adapters), then 8/8 on both; TestBSESS with TestF15 is 19/19
on each. Four mutants (cookie-POST Origin, socket Origin, content type, logout revoke), each run on both adapters: all eight
caught.

**Next.** User token expiry. The `/device` page and the pod screens of the web client (F18) can now call the server with the
cookie. `POST /v1/auth/device/approve` still allows a missing Origin (F15's rule); tighten it when F15's test is next touched.

**Surprising.** The suite's stub GitHub is steered by one shared "next login", so a second test signing people in would race
TestF15. TestBSESS plays the stub's authorize hop itself, with its own identities, instead.
